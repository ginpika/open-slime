# 圆桌 3.0 架构交叉评审结论

> 评审对象：《圆桌 3.0 · 设计结论与对 GPT6 的回应》
>
> 评审目标：在现有 Java / Spring Boot / SQLite 单机单用户架构下，明确圆桌运行时的改造边界、关键语义与实施顺序。
>
> 评审立场：以正确性、可落地性、可维护性为优先，不为抽象架构而重写已有基础设施。

## 一、总体结论

整体方向认可：保留现有 `AgentRuntime` 执行内核，将圆桌调度从 HTTP 请求生命周期中剥离，通过会话级协调器统一管理状态、调度与中断，并按阶段迁移。

当前最重要的不是重写 Agent 执行层，而是修复圆桌协调层的并发、状态提交和生命周期边界。

### 关键判断

1. **保留 Round。** Round 是讨论的因果边界；事件驱动不意味着放弃轮次。
2. **保留现有 `AgentRuntime`。** 不复制执行内核，不为了群聊重写单聊基础设施。
3. **重点重构协调层。** 但允许为取消、流式发布门控和工具权限增加必要的外围接口。
4. **默认采用确定性调度。** 不让每个 Agent 为每个事件调用模型判断是否发言。
5. **讨论阶段默认只读。** 执行操作通过提案、授权和独立 Task 完成；工具层仍需验证权限。
6. **复用现有事件设施，但先划清语义边界。** 领域事实、待执行任务和 SSE 通知可以关联，不必强行变成同一张表。

## 二、核心模型：Event、Round 与 Turn

三者属于不同层次，不应相互替代。

| 概念 | 主要职责 | 不应承担的职责 |
|---|---|---|
| `Event` | 记录系统发生的事实，驱动状态变化与调度决策 | 单独决定整场讨论的组织方式 |
| `Round` | 定义一批发言的因果边界、可见性和发布规则 | 绑定 HTTP 请求生命周期 |
| `Turn` / `AgentExecution` | 描述一次模型执行及其结果 | 决定整个圆桌何时结束 |

### 推荐的 Round 生命周期

1. 创建 Round，固定参与者、规则、讨论快照和 revision。
2. 候选 Agent 基于同一快照并行生成；允许部分成员跳过。
3. 校验执行状态、取消状态与版本。
4. 按既定顺序发布有效发言。
5. 提交 Round 结果，生成下一轮快照，或进入等待、完成等状态。

**推荐原则：并行的是推理，串行的是讨论事实的提交和轮次推进。**

事件驱动的价值主要在于响应性、恢复性、调度解耦和后续扩展，而不是取消 Round，也不是让所有 Agent 对每个事件都调用模型。

## 三、讨论阶段与执行阶段分离

### 结论

讨论阶段默认只读；需要产生副作用的操作，通过“提案 → 用户批准或明确授权策略 → 独立 Task”执行。

### 建议的阶段边界

- `DISCUSSION`：使用只读工具白名单，分析、检索、查看工作区并提出方案。
- `PROPOSAL`：输出结构化执行计划，不直接产生实际副作用。
- `APPROVED_TASK`：在授权范围内创建独立 Task。
- `EXECUTION`：工具入口再次验证 Task 授权范围，不仅依赖上层模式标记。

### M0 优先级

| 能力 | 优先级 |
|---|---|
| 阻止讨论阶段直接执行未经授权的写操作 | 必须优先 |
| 中止模型生成，并阻止已失效执行继续发布内容 | 必须优先，底层取消尽力而为 |
| 为可写工具建立执行记录、幂等或执行前状态检查 | 逐步建设 |
| 为所有外部副作用实现自动补偿 | 非 M0 前提 |

只读也不等于零风险。工具权限应通过白名单、参数校验和工具入口强制执行，而不是只依靠 Prompt 约束。

## 四、协调层与执行内核的改造边界

### 结论

第一阶段以协调层重构为主，保留现有 `AgentRuntime` 的纯执行职责。只有现有接口无法满足必要约束时，才进行最小、向后兼容的边界调整。

优先在协调层或外围适配器实现以下能力：

- 为执行附加 `executionId`、`roundId`、`revision` 等关联信息。
- 对流式片段设置发布门控，阻止取消或失效的执行继续向用户输出。
- 按讨论阶段与执行阶段应用不同工具权限。
- 将执行结果返回协调器，由协调器决定是否接受。
- 将取消信号传递到模型生成以及支持协作式取消的工具。

不要把存储、Round 状态、SSE 或调度逻辑塞回 `AgentRuntime`。

建议原则：

> 以协调层重构为中心，以执行内核保持稳定为原则；仅在取消传播、输出提交校验或工具权限隔离确实需要时，调整执行边界。

## 五、中断与旧结果处理

### 1. 区分 `CANCEL` 与 `USER_MESSAGE`

- `CANCEL`：用户明确要求停止当前讨论或执行。
- `USER_MESSAGE`：用户发送新消息。消息必须被接收和持久化，但不一定自动取消所有执行。

新消息到达后的处理建议：

1. 持久化用户消息。
2. 更新当前 Round 的输入版本或讨论约束。
3. 根据影响范围和产品策略，取消或使相关执行结果失效。
4. 阻止旧执行继续发布不再有效的内容。
5. 保留未受影响的执行，避免无谓浪费。

M0 先实现明确的用户中断语义，不实现通用 `PREEMPT` 调度策略。若预留 `priority` 字段，不必同时实现通用抢占算法。

### 2. 流式发布与版本校验

不要求所有发言都预生成后再一次性发布。推荐区分三个阶段：

1. **生成中**：模型可流式输出，但片段必须经过发布门控。
2. **发布中**：已展示的内容成为历史事实；取消后应停止后续输出。
3. **提交后**：只有通过版本检查的完整发言，才能成为当前 Round 的正式结果并影响下一轮调度。

当用户插话导致旧执行失效时：

- 持久化新输入；
- 使旧执行的发布令牌失效；
- 尽力中止模型生成；
- 拒绝继续向客户端发送旧执行返回的片段；
- 保留已经展示的部分，并标记为中断或未完成；
- 根据新输入决定是否重新生成。

已经发送到客户端的内容不能被可靠撤回，因此前端应明确区分“生成中”“已中断”和“已完成”。

## 六、调度策略：确定性优先

### 结论

默认采用确定性规则；仅在规则无法满足需求时，再评估轻量模型进行候选人选择。

| 层次 | 职责 | 是否需要 LLM |
|---|---|---|
| 确定性规则 | 轮转、指定发言者、预算、跳过、等待状态、重复发言约束 | 否 |
| 可选轻量判断 | 从候选成员中选择最适合回应新议题的成员 | 视需求决定 |
| 内容生成 | 为本轮已选中的成员生成发言 | 是 |

确定性调度不等于只能轮转。还可以基于显式议程、待回应问题、成员职责、预算和最近发言历史来选择候选人。

建议保留 `rotation` 作为可复现基线，再逐步评估 `moderator` 等策略。暂不要求每位 Agent 对每个事件执行一次 intent 判断。

## 七、状态模型

不要直接实现两个枚举的笛卡尔积，也不要把所有状态压进一个大枚举。

可考虑分离以下维度：

- **执行生命周期**：`READY / RUNNING / WAITING_EVENT / BLOCKED / COMPLETED / CANCELLED / FAILED`
- **发布状态**：`NOT_STARTED / STREAMING / PUBLISHED / ABORTED`
- **轮次参与状态**：`SELECTED / SKIPPED / DEFERRED`

这不意味着三个维度都必须永久持久化。只有确实需要恢复、审计或展示的状态才应落库；其他状态可以从执行记录和 Round 记录中推导。

必须禁止“已取消但仍持续发布内容”这类非法组合。发布门控和状态转换应明确保证这一点。

还应区分 Agent 执行状态与 Agenda / Round 状态：

- Agent 单次执行终态：`COMPLETED`、`CANCELLED`、`FAILED`。
- Agenda / Round 状态可包括：`WAITING_USER`、`WAITING_EVENT`、`BUDGET_EXHAUSTED`、`COMPLETED` 等。

轮数上限或全员沉默不等于任务成功，也不等于达成共识。

## 八、事件日志、任务与 SSE 的职责边界

### 结论

复用现有实时传输能力，但在验证现有 schema、事务和恢复语义之前，不直接把会话信令表提升为所有运行时状态的唯一正本。

建议划分：

- **领域事件**：记录 Round 创建、发言发布、取消、执行提交等事实。
- **任务 / 执行记录**：表达已启动、尚未完成、需要恢复或重试的工作。
- **SSE 通知**：负责订阅、游标、断线补推和客户端通知。

可以通过稳定的 `event_id` 关联领域事件与通知，不必新建第三套事件基础设施。

关键要求：

1. 已接收的用户输入必须可靠持久化。
2. 已提交发言与其待投递通知之间必须有可恢复的交接机制。
3. 重启后能够识别未完成执行，并按明确策略恢复、重试、取消或标记中断。
4. 不得仅凭内存队列认定工作已经可靠排队。
5. 事件日志记录“发生了什么”；任务记录还需要表达“接下来需要完成什么”。

对 SQLite 单机应用，可先复用现有 `task` 结构表达 Round 推进或 AgentExecution 生命周期；是否增加 Agenda 专表应由现有 schema 能否清晰表达这些语义决定。

## 九、单写者与异步执行

单写者是指同一会话的调度状态只能由一个逻辑协调入口提交变更，不代表协调器必须在一个线程中阻塞等待所有工作。

推荐模型：

1. 用户输入、取消、执行完成等事件进入会话级协调入口。
2. 协调器串行处理状态变化与调度决策。
3. 模型和工具工作在协调器之外异步运行。
4. 执行完成后以事件或回调形式返回。
5. 协调器校验版本与状态后，再决定是否提交结果。

`BlockingQueue`、单会话串行 executor 或其他 mailbox 都可以作为实现方式。M0 不必引入通用 Message Bus；内存队列也不能替代持久化与恢复机制。

所有状态写入路径都必须纳入协调模型，包括用户消息、停止按钮、Agent 完成、工具回调、Round 收场和进程恢复。不能保留绕过协调器的旁路写入。

## 十、迁移顺序与验收标准

### P0：并发止血与安全边界

- 修复同一会话的并发推进和停止槽位竞争。
- 梳理所有状态写入路径，避免协调器旁路。
- 增加旧执行结果的版本校验。
- 阻止讨论阶段执行未经授权的写操作。

**验收：** 并发发消息和停止不会产生冲突状态；旧执行不能污染新状态或继续发布失效内容；讨论阶段无法绕过只读权限。

### P1：非阻塞 Agenda

- 将 `advance()` 拆成单次状态跃迁。
- 协调器负责状态和调度，模型与工具执行在外部异步运行。
- SSE 只负责订阅与投递，不再承担整轮执行的生命周期。

**验收：** 模型调用期间，用户输入和取消事件仍可被及时处理；SSE 断开不会使讨论生命周期与请求绑定。

### P2：持久化与恢复

- 明确领域事件、任务执行记录和 SSE 通知的边界。
- 为已接收但未完成的执行建立可恢复状态。
- 建立发言提交与通知投递之间的可靠交接机制。

**验收：** 进程退出后，未完成任务不会被误判为成功，也不会无条件重复执行有副作用的操作。

### P3：Round 与上下文

- 明确 Round 生命周期和发布规则。
- 为成员引入上下文 cursor 与增量投递。
- 让 `contextWindow` 和 token 预算真正生效。
- 使用结构化事件类型，避免前端依赖中文文案判断事件语义。

**验收：** 轮次可见性与因果关系明确；上下文截断不会无意丢掉关键的最新输入。

### P4：受控并行与主持人策略

- 在同一快照上并行生成候选发言。
- 按既定顺序串行发布与提交。
- 保留可复现的 rotation 基线。
- 逐步引入主持人策略，必要时再评估轻量模型选人。

**验收：** 同一轮的发言不会互相污染；并行不会导致不必要的 intent 调用和成本失控。

### P5：完整执行工作流

- 将提案审批、独立 Task、工具审计和恢复流程收口。
- 为适用的工具完善协作式取消、幂等和失败处理。
- 按实际需要补充执行补偿机制。

**验收：** 讨论、授权和执行是可区分、可追踪的流程；重复执行和失败处理有明确策略。

> 阶段式迁移不代表每个阶段都完全不改变语义。每阶段应明确必须保持的既有行为、需要修复的缺陷行为、新增行为及对应回归测试。

## 十一、实施前需要确认的设计问题

编码前建议确认以下事项：

1. 所有圆桌状态写入是否都能经过会话级协调入口？
2. `POST /chat/stop`、用户新消息、Agent 完成回调是否存在绕过协调器的路径？
3. 现有 `session_events` 与 `roundtable_topic_event` 的 schema、事务边界、保留策略和幂等语义分别是什么？
4. 现有 `task` 能否表达 Round 推进与 AgentExecution 的恢复生命周期？
5. 流式发布是否具备可校验的执行 ID、版本与取消门控？
6. 讨论阶段的只读权限能否由工具入口强制执行？
7. P0 是否有覆盖并发消息、停止竞争、旧结果返回和进程中断的回归测试？

如果这些问题尚未确认，不应仅凭架构描述断言现有实现已经满足相应要求。

## 十二、最终决议

本次评审建议形成以下架构决议：

- **Round 是一等领域概念，保留其因果边界。**
- **Event 驱动状态变化与调度，不取代 Round。**
- **保留现有 `AgentRuntime`，以协调层重构为主。**
- **并行推理、受控发布、串行提交。**
- **默认确定性调度，不为每个事件调用所有 Agent 的 intent 模型。**
- **讨论阶段默认只读；执行通过提案、授权和独立 Task 完成。**
- **旧执行结果必须经过版本检查；流式输出也必须经过发布门控。**
- **复用现有事件与 SSE 设施，但明确领域事实、待执行任务和通知投递的职责边界。**
- **先解决正确性与恢复性，再推进并行、主持人和高级调度策略。**

最终目标不是构建一个抽象的通用多 Agent 平台，而是让现有执行内核、圆桌领域模型和会话事件设施之间的并发、状态提交与生命周期边界可靠、可测试、可维护。
