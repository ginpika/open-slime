## 已定位的问题

### 1. 整批结束后才能再次派工，不能持续补位

`CollaborationPlan.dispatchBatch` 只允许 `phase='planning'`；`returned` 在任何同批工作仍在途时不返回 planning。`RoundtableTaskTools` 同样禁止在 executing/checking 阶段创建或追加派工。这是上一轮实现采用的批次边界，现在的真实运行证明它限制了持续并行。

实例：

- 两个场景实现的所有声明前置在 16:24:33 已完成，但直到 16:35:29 才启动。期间同批入口页工作直到 16:34:08 才以受阻退出。约 10 分 56 秒的延迟与整批等待一致，其中还包含主控重新规划的时间。
- 设计令牌收敛 `ee5ff209` 的声明前置在 16:57:29 已完成；它不依赖入口页，并且声明的写入范围与入口页不重叠。然而主控连续三次只派入口页，令牌工作直到 17:23:19 才启动，晚约 25 分 50 秒。此处还存在主控未利用已就绪工作的规划遗漏，不能全部归因于线程调度器。

建议 P1 修复：按单项授权保存派工代次；已完成项及时通知主控，让主控明确追加就绪工作，不撤销其他在途授权。不能只删除 planning 检查：当前会话级 version 的变化也会使旧编码执行授权失效。继续保留主控派工权、独立副本、重叠路径冲突检查与整合验证。

### 2. 进程清理失败后，副本进入反复恢复失败的状态

数据库底层证据，而非仅引用 Agent 总结：

- `c14e9328` 的 `process.started` 在 16:25:10 记录了后台启动 dev 并使用 `pkill -TERM -f "npm run dev"`、`pkill -TERM -f "vite"` 和 `pkill -KILL -f "vite"` 的命令。
- 该 run 后续共 7 个 attempt；第 2–7 次都在 PREPARING 后很快 FAILED/INTERRUPTED，错误重复为 `进程组停止未确认`。
- 主控两次尝试 cancel（16:34:32、17:00:22），`tool_execution` 明确记录因“仅当前有效派工的执行者”权限检查而被拒绝。
- 第二份副本 `7e7ac30c` 在 17:06:29 的命令使用了 `nohup npm run dev ... &`；之后同样 INTERRUPTED，attempt 2 在 PREPARING 时再次失败。
- 当前入口接线 run `8408f2fc` 在 17:28:20 也记录了同类 BLOCKED 验证，说明该问题仍会发生。

机制：`WorkspaceCommands.stopAll` 清理失败后保留本地进程 marker；`recover` 直接再次调用同一 stopAll，而 `CodingFacade` 在给模型工具之前先 recover。与此同时，同 TODO 的 start 强制返回已有未完成副本，主控 cancel 又借用执行者的 continueRun 授权。最终出现“不能恢复、不能由主控终止、不能在同 TODO 安全换副本”的闭环，主控只能放弃 TODO 并新建替代条目。

建议 P0 修复：增加主控可审计的停止/恢复授权，提供同 TODO 保留旧成果后创建替代执行的路径，以及独立于普通编码循环的进程诊断/清理流程。不能直接清 marker、忽略错误或放宽进程身份检查。是否还存在清理时序竞争、PID/进程组识别问题，需要远端 PID/PGID、进程状态和已有 group-state 文件进一步核实；本轮只读数据库检查没有证明具体 Linux 进程清理失败的全部细节。

### 3. 整合了依赖声明，却沿用旧的安装环境

`ed9bd772` 在 16:07:41 记录 artifact.integrated，随后 16:08:22、16:09:37 两次独立验证均报 `TS2307 / ERR_MODULE_NOT_FOUND: @tailwindcss/vite`。`0a8660a4` 的 16:10:28 验证同样报缺包。

源码机制与错误一致：整合刷新源码/依赖声明，`WorkspaceProjects.pushExecution` 明确保留 node_modules 等依赖和构建产物；独立 verify 直接重跑原命令，不判断依赖清单/锁文件与已安装环境是否一致。主控因此将三项已经做过实现的工作重新派给执行者刷新环境，其中至少两项的缺包失败有直接验证事件支持。主界面模型那项还涉及验证命令吞退出码，不能仅据它曾显示 PASSED 就认定验证成功。

建议 P1 修复：将源码版本与环境准备版本分开追踪；整合改变依赖指纹时运行项目显式配置的准备步骤，或返回“环境待准备”状态。不要把缺依赖直接解释为业务代码不合格，也不要在未知项目中硬编码 npm 安装命令。

### 4. 展示没有清楚区分在途、排队、编码和检查

四个协作 worker 同时存在，但前两个编码 run 之外的两项实际等待了约 7 分钟和 11 分钟。现有“执行中 / N 项在途”表达容易让人误以为编码并发从四个下降了。

建议 P2 改进：分别展示编码运行、等待名额、待检查/检查中与受阻数量。保留同一检查成员按序检查和冲突时拒绝覆盖，不应为了维持表面并发数而移除这些约束。
