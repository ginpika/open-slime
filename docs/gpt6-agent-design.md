# **设计一**

你提到的是多 Agent 群聊架构里一个非常核心的问题：Turn 是模型推理的边界，不应该成为整个群聊系统的调度边界。

如果你的 Personal Agent 仍然以“用户输入 → 调用模型 → 等待模型输出结束 → 再调用下一个 Agent”为核心循环，那么即使你创建了十个 Agent，本质上也只是一个串行的多模型工作流，而不是真正具有异步性和打断能力的群聊系统。

我建议你把设计从 Turn-based Runtime（轮次驱动） 转向 Event-driven Runtime（事件驱动），再在上面构建一个支持抢占、并发、打断和恢复的讨论引擎。

## **一、先把三个概念彻底分开**

<br />

1. Turn：一次模型调用

模型收到上下文，开始生成，最终返回结果或工具调用。它是推理过程的边界，不是群聊的边界。

<br />

1. Conversation：持续存在的讨论

一个讨论可以持续数分钟、数小时，甚至跨越多个 Session。不同 Agent 可以并发思考、发言、等待、被唤醒，而不要求所有人依次完成一轮。

<br />

1. Runtime：持续运行的事件处理系统

负责接收用户消息、Agent 报告、工具结果、定时事件，判断事件影响谁，哪些任务要暂停、取消、恢复或重新调度。

关键在于：Agent 可以完成一个 Turn，但讨论并没有结束；Agent 可以保持沉默，但后台任务仍然运行；用户可以在任何时候发言，而不必等待当前 Turn 结束。

## **二、你真正需要的架构：事件驱动 + 可抢占的 Agent 执行器**

<br />

Event Ingress

用户消息 / Agent 报告 / 工具结果 / 定时器 / 外部 Webhook

<br />

Event Log + State Reducer

事件持久化、更新共享状态、版本控制

<br />

Scheduler / Interrupt Manager

优先级、唤醒、抢占、取消、恢复、预算控制

<br />

Agent Workers

并发推理、可中断等待

<br />

Tool Workers

异步执行、回调、结果验证

<br />

Shared State + Message Bus

任务、消息、证据、决策、待办、执行状态

这套架构中有三个特别重要的设计。

- 事件日志是事实来源。 任何用户输入、工具结果和 Agent 报告，都先成为系统事件，而不是直接塞进某个正在运行的模型上下文。
- 调度器决定谁应该运行。 Agent 只负责推理和提出行动，不负责决定整个系统何时停止、谁可以抢占谁。
- Agent 执行必须可恢复。 新事件到来时，可以中断当前推理、标记结果过期、保留已完成工作，然后基于最新状态重新生成。

注意：事件驱动不等于每来一个事件就调用一次大模型。大部分事件应该由普通代码处理、合并或过滤，只有确实需要智能判断时才触发模型调用。

## **三、打断到底怎么实现？不能只靠给 Agent 发一条新消息**

这里有一个工程上的关键事实：大多数模型 API 的一次生成，并不能像真人聊天一样，在任意位置暂停、保存内部思维状态，然后稍后从原地继续。

所以你要实现的是系统层的打断，而不是假设模型本身支持任意暂停。

我建议把打断分成四种。

**类型**

**例子**

**Runtime 的处理方式**

`INTERRUPT`

用户补充了新要求，改变当前任务

取消或停止旧生成，更新目标后重新调度

`PREEMPT`

高优先级事件到达

暂停低优先级任务的调度资格，先处理紧急任务

`NOTIFY`

场外 Agent 发现新证据

写入事件日志，判断哪些 Agent 需要被唤醒

`CANCEL`

用户明确要求停止

取消相关生成和可取消的工具任务，清理后续调度

这些操作不能混为一谈。比如，收到一个普通的场外 Agent 报告，并不意味着必须取消所有正在运行的模型；它可能只需要更新共享状态，并唤醒一个相关 Agent。

### **场景 B：场外 Agent 突然报告重要发现**

假设讨论室里正在设计数据库结构，安全 Agent 在另一个任务中突然报告：

> 发现当前设计会把用户的 API Key 写入普通日志。

这不应该等待当前讨论完成，更不应该简单地把消息排在聊天记录末尾。

建议处理为：

- 安全 Agent 发布一个带有来源、证据和影响范围的事件。
- Runtime 判断事件的严重性，以及它与哪些任务、决策相关。
- 若存在凭据泄露风险，立即暂停相关的日志写入或部署操作。
- 唤醒负责日志设计的 Agent，以及必要的验证 Agent。
- 将已有的架构决策标记为“需要重新验证”，而不是直接删除历史决策。

但要区分两个动作：紧急安全措施可以由确定性的策略直接触发；修改架构方案则交给相应 Agent 分析。 不应为了等大模型判断，延迟那些已经明确配置好的保护措施。

## **四、每个 Agent 应该有自己的执行状态机**

我不建议继续使用单一的 `ACTIVE / SILENT` 状态描述整个 Agent。它无法回答：Agent 是在生成、等待工具，还是只是暂时不说话？

更适合的设计是把状态拆成两个维度。

### **发言状态（Communication State）**

SPEAKING

LISTENING

SILENT

控制是否向讨论室发言，以及是否需要向其他 Agent 发布消息。

### **执行状态（Execution State）**

READY

RUNNING

WAITING\_EVENT

BLOCKED

COMPLETED

CANCELLED

控制任务是否在运行、等待依赖、被阻塞，或已经完成。

例如：

- `SILENT + RUNNING`：Agent 不在讨论室发言，但正在执行分析。
- `SILENT + WAITING_EVENT`：Agent 不发言，正在等待工具返回。
- `LISTENING + READY`：Agent 正在监听事件，有任务时可以被调度。
- `SILENT + COMPLETED`：当前任务完成，不代表它永久退出讨论。

这样，你前面设计的“全员沉默后进行情景决策”就可以更准确地实现：判断的不是所有 Agent 有没有发言，而是当前有没有尚未完成、可推进、可解阻的工作。

## **五、实现抢占时，需要特别处理三个工程问题**

### **1. 不要让旧结果覆盖新状态**

每个任务维护一个递增的 `revision` 或 `generation`。

比如 Architect 基于 `revision=12` 开始生成方案。用户新输入到达后，任务变成 `revision=13`。

旧生成即使稍后返回，也必须经过版本校验：

```
if result.revision != task.current_revision:
    mark_result_stale(result)
    # 不允许直接覆盖当前决策
else:
    commit_result(result)
```

旧结果未必毫无价值，可以保留为证据或草稿，但不能自动当作最新结论。

### **2. 取消生成，不等于取消工具副作用**

如果模型正在生成文本，通常可以尝试取消请求或停止读取流式输出；但具体 API 是否能真正终止服务端计算，要看模型服务的实现。

如果模型已经发起工具调用，例如发送邮件、删除文件、部署服务，就不能仅靠取消模型请求来保证操作停止。

因此，工具调用最好具备独立的执行记录和生命周期：

- 尚未开始：可以取消。
- 正在执行：根据工具是否支持安全取消决定。
- 已经执行：记录结果，并根据需要采取补偿操作。
- 结果不确定：先查询执行状态，不能盲目重试。

对支付、删除、部署等有副作用的操作，还应使用幂等键、权限校验和明确的授权策略。

### **3. 避免事件风暴**

如果每条 Agent 消息都唤醒所有其他 Agent，你的系统很快就会陷入大量重复推理，成本和延迟都会失控。

建议采用“事件订阅 + 相关性路由 + 事件合并”：

- 只有订阅相关主题或任务的 Agent 才被唤醒。
- 同一任务短时间内的多个普通通知可以合并处理。
- 用户新指令、明确取消、严重安全事件不应被普通通知合并掉。
- 同一个事件被重复投递时，使用 `event_id` 去重。

## **六、我建议采用的事件协议**

不需要一开始就上复杂的分布式消息系统。先定义统一的事件结构即可：

```
class RuntimeEvent:
    event_id: str
    event_type: str
    source: str
    target: str | None
    task_id: str | None
    priority: int
    created_at: str
    payload: dict
    correlation_id: str | None
```

事件类型可以包括：

```
USER_MESSAGE
AGENT_MESSAGE
AGENT_REPORT
TASK_CREATED
TASK_BLOCKED
TASK_COMPLETED
TOOL_STARTED
TOOL_COMPLETED
TOOL_FAILED
DEADLINE_REACHED
INTERRUPT_REQUESTED
CANCEL_REQUESTED
```

再为每个事件定义处理策略：哪些只更新状态，哪些唤醒 Agent，哪些需要抢占，哪些需要用户确认。

注意，`priority` 只是排序依据。真正的抢占行为还需要明确的策略，例如用户明确取消任务应高于普通讨论消息，而一个普通的 Agent 报告不应无条件中断所有任务。

## **七、技术落地建议**

如果你仍然以 Python 为主要技术栈，我会从以下组合开始：

- 运行时： `asyncio`，用独立任务运行 Agent 推理和工具调用。
- 事件入口： 统一的异步事件队列，保证所有外部输入都先进入 Runtime。
- 持久化： SQLite 起步，使用事务记录事件、任务状态和调度意图。
- 并发控制： 每个任务使用版本号；共享状态更新通过事务或受控写入完成。
- 模型调用： 统一的 Model Gateway，封装流式输出、超时、取消和重试。
- 工具执行： 独立的 Tool Gateway，管理授权、幂等性、执行状态和副作用。

在单机个人 Agent 阶段，不必为了追求“真正的实时系统”而立即引入 Kafka、复杂微服务或分布式 Actor 框架。先保证事件不丢失、状态一致、任务可恢复，再考虑横向扩展。

最后，我认为这套架构里最值得确立的一条原则是：

Agent 负责思考和提出行动，Runtime 负责调度和控制执行；Turn 是一次推理，Event 才是系统推进的基本单位。

只要把这条边界建立好，你之前提出的自由群聊、沉默决策、场外报告、用户随时插话、工具异步返回，其实都可以统一到同一个事件驱动运行时里，而不需要为每一种情况单独设计一套流程。

# **设计二**

我反而觉得，你现在不应该急着把单聊和群聊重新拆成两套代码。你可能需要返工，但返工的重点应该是重新划分架构边界，而不是把之前合并的东西全部拆回去。

你之前合并为 `Turn + AgentRuntime`，不一定是错误。真正的问题在于：你很可能把“如何运行一个 Agent”和“如何组织多个 Agent 之间的持续协作”也一起合并了。

这两件事有很大的区别。

- 单聊和群聊可以共用模型调用、上下文构建、工具执行、记忆、权限、成本统计等基础能力。
- 但单聊和群聊的对话生命周期、消息路由、调度策略、并发控制和中断语义不应该被一个简单的 Turn 循环绑死。

因此，我的建议是：保留已经写好的 `AgentRuntime`，在它上面增加独立的 `ConversationRuntime` 或 `SessionRuntime`，而不是复制一份 AgentRuntime 给群聊使用。

## **一、先决定哪些要共用，哪些必须分开**

## **Shared Agent Platform**

单聊和群聊共同使用的底层能力

<br />

AgentRuntime

单次推理、上下文、模型调用、工具调用、结果解析

<br />

Execution Services

权限、预算、超时、取消、执行记录、审计

<br />

State & Memory

消息持久化、任务状态、记忆、共享工件

<br />

Model & Tool Gateway

模型适配、工具注册、重试、幂等、错误处理

### **Direct Conversation Runtime**

单聊策略：用户输入、Assistant 回复、工具循环、回复完成

### **Group Discussion Runtime**

群聊策略：多方消息、异步唤醒、讨论调度、打断、沉默决策

两种 Runtime 共用底层 Agent 执行能力，但拥有不同的生命周期和调度策略。

这里有个很重要的细节：不要让 `AgentRuntime` 自己决定整个讨论何时结束。 它可以判断一次模型生成是否完成、工具调用是否结束、一次 Agent 执行是否成功；至于整个群聊是否继续、等待用户还是结束，应由群聊的协调器决定。

## **二、我会怎么设计 Java 版本**

我会把架构划分为四层。这里的重点不是类名，而是每一层对什么事情拥有决定权。

<br />

第一层：Conversation / Room

负责单聊或群聊的业务语义。

单聊维护当前用户请求和回复生命周期；群聊维护参与者、讨论主题、待解决问题、讨论状态和结束条件。这里不直接执行模型调用。

<br />

第二层：Orchestrator / Scheduler

负责决定下一步应该发生什么。

单聊可以使用简单的请求驱动策略；群聊使用事件驱动策略，负责路由消息、唤醒 Agent、处理沉默、判断阻塞、响应打断以及分配执行额度。

<br />

第三层：AgentRuntime

负责执行一次 Agent 工作。

接收执行请求，构建上下文，调用模型，处理流式输出与工具调用，返回结构化结果。它不直接控制其他 Agent，也不决定整个讨论是否结束。

<br />

第四层：Infrastructure

负责可靠执行的基础设施。

包括持久化事件、消息总线、任务队列、模型网关、工具网关、状态存储、日志与指标。

注意，这四层是逻辑架构，不代表你必须部署四个微服务。对你的 Personal Agent，我更倾向于先做成一个 Java 模块化单体。

## **三、在 Java 中，Turn 应该保留，但不能再做唯一的调度单位**

你不需要把 Turn 删掉。Turn 仍然是很有用的概念，只是要把它放到正确的位置。

建议区分以下几个对象：

**对象**

**生命周期**

**作用**

`Conversation`

较长，可持续存在

单聊或群聊的整体会话

`Event`

一次事件的记录

用户输入、Agent 报告、工具完成通知等

`Task`

从创建到完成或取消

需要推进的一项工作

`AgentExecution`

一次执行过程

某个 Agent 执行任务的生命周期

`Turn`

一次模型交互

一次模型请求及其生成结果

`ToolExecution`

一次工具执行

工具的启动、执行、结果及副作用记录

例如，用户发起一个群聊任务：

1. 创建 `Conversation` 和初始 `Task`。
2. 群聊调度器决定唤醒 Architect 和 Researcher。
3. 两个 Agent 分别创建自己的 `AgentExecution`，各自执行一个或多个 Turn。
4. Researcher 完成工具调用，产生一个 `AGENT_REPORT` 事件。
5. 调度器发现报告与 Architect 的任务有关，通知 Architect 更新工作。
6. 用户在此时插话，Runtime 更新任务约束，并判断哪些执行需要取消。
7. 相关 Agent 根据最新状态继续推进，最终由群聊调度器判断是否完成。

整个群聊跨越多个 Turn，但不需要存在一个巨大、不断递归的 Turn。

```
public interface AgentRuntime {
```

这里有一个实现层面的提醒：`CompletionStage` 适合表示异步完成，但它本身不提供持久化、抢占或恢复能力。实际的取消操作也应该有独立的执行标识和取消语义，而不是只依赖 `CompletableFuture.cancel()`。

此外，群聊调度器最好以事件驱动状态转移为核心，而不是在一个 `while` 循环里不断让模型判断下一步。

## **四、你最应该避免的是“为了群聊，重写所有底层能力”**

我会按以下顺序改造，尽可能复用已有代码。

1. 先冻结现有 AgentRuntime 的职责

   明确它只负责单个 Agent 的执行，不直接决定群聊的轮次、其他 Agent 的唤醒和整个会话的结束。
2. 引入统一的事件模型

   用户输入、Agent 消息、工具结果都转换为 `RuntimeEvent`。先把事件记录与状态更新做好，不需要立刻实现复杂抢占。
3. 先做一个最小的 GroupDiscussionRuntime

   只支持创建讨论、分发消息、唤醒 Agent、收集结果、判断是否继续。暂时不要同时实现复杂的自由群聊、动态角色分配和多层子 Agent。
4. 再增加异步事件和打断

   加入用户插话、场外 Agent 报告、取消旧生成、版本校验、任务恢复等能力。
5. 最后完善讨论决策引擎

   把你之前设计的全员沉默决策、继续推进、等待用户、结束话题，以及等待外部事件整合进调度器。

每个阶段都应当有独立的测试。特别是：用户插话不能丢失、旧结果不能覆盖新约束、同一事件重复投递不能重复执行副作用、一个 Agent 失败不能让整个讨论永久卡住。

## **五、什么情况下才真的需要拆开两套架构？**

我会用一个简单的判断标准：

- 如果单聊和群聊只是同一种生命周期下的不同提示词与参与者数量，就没必要拆开。
- 如果单聊是一次用户请求驱动的执行循环，而群聊需要持续运行、异步事件、并发参与者、独立任务生命周期和全局协调，那么就应该拆开它们的协调层。
- 如果未来两者连部署、可靠性、吞吐和故障隔离要求都完全不同，再考虑拆成不同进程或服务。

所以我的建议是：拆开协调逻辑，不拆重复的执行基础设施。

你之前合并的代码不一定浪费了。模型调用、工具执行、上下文管理和执行记录依然可能是很好的基础。真正需要审查的是：这些模块是否错误地依赖了“当前 Turn 完成后，系统才能做下一件事”的假设。

最后，我觉得在你正式动手之前，有一个比选择消息队列或异步框架更重要的事情：

先确认你当前的 `AgentRuntime` 到底承担了多少职责。

如果它目前既负责模型调用，又负责消息路由、群聊循环、Agent 选择和结束判断，那么重构范围会比较大；如果它只是一次 Agent 执行器，你可能只需要在外围补出事件系统和群聊协调器。

你可以把目前 Java 项目里的核心调用链贴出来，尤其是 `AgentRuntime`、Turn 的执行入口、消息分发，以及 Agent 执行结束后由谁决定下一步。我可以据此帮你做一次保留现有代码的架构迁移设计，明确哪些类保留、哪些职责迁移、哪些接口新增，而不是建议你推倒重写。
