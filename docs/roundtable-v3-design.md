# 圆桌 3.0 设计（定稿）

> 状态：**定稿**。已与 GPT6 交叉评审两轮（对象：`docs/gpt6-agent-design.md`；外部评审纪要：`docs/roundtable-3.0-architecture-review.md`），结论已收敛。
> 范围：`agent.roundtable` 全模块 + 与 `agent.chat` 的执行器边界 + 后端实时层。
> 约束：Java / Spring Boot / SQLite，单机单用户（M0），自付 API 成本。
> 一句话主张：**执行内核不动，把调度从 HTTP 请求栈里搬到一个常驻的会话级协调器；先保正确性，再谈并行。**

---

## 0. 结论（五条）

1. **「设计二」就是我们的现状，守住不动。** `AgentRuntime` 承担 0 个存储职责、0 个调度职责，只有「模型往返 + 工具批 + 结构分段」，是一个约 260 行、进出只经 `Spec` / `Result` / `RunState` 的纯执行内核；`ChatExecution` 就是「可替换点」接口。**不复制执行内核，不为了群聊重写单聊基础设施。**
2. **缺的是「设计一」的中间层：议程（Agenda）。** 它现在的形态是 `RoundtableTopicService#advance` —— 一个把「选人 + 阻塞执行 + 收场判定 + 落库 + 推流」揉在一起、并绑死在一次 HTTP 请求栈里的串行 `while`。这是唯一必须动范式的点。
3. **Round 是一等领域概念，保留。** 并行的是**推理**，串行的是**讨论事实的提交**与轮次推进。事件驱动不取消轮次。
4. **正确性优先于并行。** 现状存在并发交错写入、停止失灵、只读可绕过三个**正在发生**的缺陷；在这些修掉之前，任何并行/主持人的推进都是在流沙上盖楼。
5. **执行操作与讨论分离。** 讨论阶段默认只读；产生副作用的操作走「提案 → 授权 → 独立 Task」，且权限必须由**工具入口**强制，不能只靠提示词约束。

## 1. 现状证据（代码事实）

| # | 事实 | 位置 |

| ① | **编排绑在请求栈里**：控制器用虚拟线程同步跑完 `topics.sendMessage(...)`，SSE 生命周期 = 整轮生命周期（300s 上限）。断线后生成继续，但没有任何方式接回进行中的一轮。 | `AgentController#chatStream` |

| ⑤ | **上下文全量重放且 `contextWindow` 被忽略**：每次发言把最近 128 **条**消息（按行截断，可能把用户本轮问题截掉）压成唯一一条 user；成本 O(轮 × 人 × 全场)。 | `RoundtableChatService#dispatch` / `#recent` |
| ⑥ | **状态投影靠全表重放，且用「名字」当 key**：`states()` / `participants()` / `latestDesires()` 每次都 `byTopic()` 全表查 + 折叠；`toTopicView` 输出 `Map<name, state>`，两名成员重名会互相覆盖。 | `RoundtableTopicService#toTopicView`、`TopicStateMachine#states` |
| ⑦ | **只读可由入口绕过（真实缺口）**：`CapabilityGuard#check` 对 `grant == null` 与 `allAccess()` 一律放行；圆桌 `capabilityTracked()=false` → 授权为 `null` → **放行**。`runTool` 是**按名字分发**的，不看本次发出去的工具面，故模型凭幻觉调 `delete_graph_item` / `create_document` / `upsert_node` 会被真实执行。 | `CapabilityGuard#check`、`RoundtableChatService#runTool` |
| ⑧ | **desire 记的是假原因**：`DEFAULT_DESIRE = 10`（**上界**，漏报者与最想说话者平手）；`latestDesires` 后报盖先报且**永久有效**，上一轮报高分、这一轮漏报的人继续排在队首。 | `DesireSpeakerStrategy#DEFAULT_DESIRE`、`TopicStateMachine#latestDesires` |
| ⑨ | **收场靠协商**：`settle` = 全体提议结束 → 否则向沉默者征询 → 重开封顶 → 到顶按「沉默=同意」收束；且被征询未表态者被直接记成「提议结束」（**把猜测写成事实**）。 | `RoundtableTopicService#settle` / `#advance` |
| ⑩ | **工具副作用无独立生命周期**：成员可在自动推进链里执行 `run_command`，而这条流 `taskTracked=false` → 不落 `task`，无取消/补偿语义。 | `RoundtableChatService#terminalTool` / `#taskTracked` |

## 2. 核心模型：Event / Round / Turn

三者属于不同层次，互不替代。

| 概念 | 主要职责 | 不承担的职责 |
|---|---|---|
| `Event` | 记录系统发生过的事实，驱动状态变化与调度决策 | 单独决定整场讨论的组织方式 |
| `Round` | 定义一批发言的**因果边界、可见性与发布规则** | 绑定 HTTP 请求生命周期 |
| `Turn` / `AgentExecution` | 描述一次模型执行及其结果 | 决定整个圆桌何时结束 |

**Round 生命周期（目标）**

1. 创建 Round：固定参与者、规则、讨论快照与 `revision`。
2. 候选成员基于**同一快照**并行生成（允许部分成员跳过）。
3. 校验：执行状态、取消状态、`revision`。
4. 按既定顺序**串行发布**有效发言。
5. 提交 Round 结果，生成下一轮快照，或进入等待 / 完成状态。

> **并行的是推理，串行的是讨论事实的提交和轮次推进。**

## 3. 目标运行时

只有中间那一层是新的。

```
        ┌────────────────────────────────────────────┐
        │  会话事件流（SSE 订阅，可断线重连）          │
        │  Last-Event-ID 补推 · 现成能力              │
        └───────────────────┬────────────────────────┘
                            │ 投递事件
        ┌───────────────────▼────────────────────────┐
        │  议程 Agenda · 调度器          【新增】      │
        │  per-session 单写者 · 事件驱动 · 可抢占      │
        │  领域事件正本 + 内存状态投影 + 收场裁定      │
        └───────────────────┬────────────────────────┘
                            │ 调度执行
        ┌───────────────────▼────────────────────────┐
        │  AgentRuntime（现有内核，保持稳定）          │
        │  模型往返 + 工具批 + 分段                    │
        └───────────────────┬────────────────────────┘
                            │ 调用能力
        ┌───────────────────▼────────────────────────┐
        │  能力平面：工具 · 终端 · RAG · 记忆          │
        └────────────────────────────────────────────┘
```

**内核唯一必要的改动**：给 `ToolDispatch` 暴露取消 / 版本信号（当前只有 `run(JsonNode)` 与 `parallelizable(String)`，`ToolBatch` 一旦提交到线程池即不可撤）。
发布门控与提交校验**不需要改内核**——前者用 `Listener.deltaListener(round)` 返回的 `DeltaListener` 作闸门，后者由协调器在 `recordChat` 前判定（`Spec.runState()` 与 `Result` 本就由调用方持有）。

## 4. 六项改造

### 4.1 议程化：`/chat/stream` 只做「投事件 + 订阅」

`POST /api/agents/chat/stream` 变成：append 一条 `USER_MESSAGE` 事件 → 订阅该会话事件流 → 立刻返回 emitter。编排由常驻的 `RoundtableAgenda`（per-session 串行队列）驱动；`advance` 拆成「一次状态跃迁」，被议程反复调用。

**一举解决 ①②③④**：单写者天然消灭 floor 覆盖 / 双 SPEAKING / 停止槽位互顶；SSE 断线既不丢生成也不丢可见性。

**议程与单写者的边界**：单写者 = 同一会话的调度状态只能由一个逻辑协调入口提交，**不代表协调器要阻塞等待所有工作**。模型与工具在协调器之外异步运行，完成后以事件 / 回调返回，协调器校验版本与状态后再决定是否提交。
所有状态写入路径都必须纳入协调模型（用户消息、停止按钮、Agent 完成、工具回调、Round 收场、进程恢复），**不留旁路**。

### 4.2 事件模型显式化

`roundtable_topic_event` 已是 append-only 正本（`seq` 是话题内**持久**序号，折叠排序可靠）。补 `event_id`（幂等去重）与清理策略即可。

**职责三分（不合并成一张表）**：

| 角色 | 落点 | 职责 |
|---|---|---|
| 领域事实 | `roundtable_topic_event` | Round 创建、发言发布、状态跃迁、取消 |
| 执行生命周期 | `task` | 已启动、未完成、需恢复 / 重试的工作（记「接下来要完成什么」） |
| 通知投递 | `session_events` + SSE | 订阅、游标、断线补推 |

三者靠稳定的 `event_id` 关联。
> 不把 `session_events` 提升为运行时状态的唯一正本：它的 `seq` 是内存 `AtomicLong`（重启归零）、无保留策略、`since(afterId)` 按全局 id 补推不带会话过滤，且语义是「有新消息 / 答完了」信令。

状态投影改为**常驻内存**（在单写者线程里增量维护），落库只做持久化。

### 4.3 打断分级（先落两类，留两个位）

| 类型 | 触发 | 落地 |
|---|---|---|
| `USER_MESSAGE` | 用户插话 | 持久化消息 → 更新 Round 输入版本 → 按影响范围取消 / 失效相关执行 → 阻止旧执行继续发布 → 保留未受影响者 |
| `CANCEL` | 停止按钮 | runId / epoch 取消，替掉「每会话一个 AtomicBoolean」 |
| `PREEMPT` | 高优先级事件 | **M0 只预留 `priority` 字段，不实现通用抢占算法**；仅实现「用户取消立即生效」 |
| `NOTIFY` | 场外 Agent 报告 | 留位（当前无此事件源） |

要区分 `CANCEL` 与 `USER_MESSAGE`：**新消息必须被接收和持久化，但不一定自动取消所有执行。**

### 4.4 状态模型：三个维度，按需落库

不用一个大枚举，也不做两维笛卡尔积。

| 维度 | 取值 | 说明 |
|---|---|---|
| 执行生命周期 | `READY / RUNNING / WAITING_EVENT / BLOCKED / COMPLETED / CANCELLED / FAILED` | 描述这次执行走到哪 |
| 发布状态 | `NOT_STARTED / STREAMING / PUBLISHED / ABORTED` | 描述内容有没有出门 |
| 发言机会与参与 | 见 §5（`selection` + `participation` + `reason_code`） | 描述**为什么没说话** |

只有需要恢复、审计、展示的状态才落库，其余从执行记录与 Round 记录推导。
**必须禁止「已取消但仍持续发布内容」这类非法组合**——由发布门控保证。

另外要区分 Agent 执行终态（`COMPLETED / CANCELLED / FAILED`）与 Agenda / Round 状态（`WAITING_USER / WAITING_EVENT / BUDGET_EXHAUSTED / COMPLETED` 等）。

### 4.5 状态机瘦身：收场由议程条件决定

「要不要说」降级为**每轮一次 intent**（无历史、无折叠）。`ask_user` 落成 `WAITING_EVENT`。
收场改由议程条件判定（目标达成 / 轮数上限 / 主持人裁定 / 用户叫停）→ 删掉 `prompt / reopen / markClosing / reviveSilent / 全体判定 / maxResolveRounds`。

> **重要修正**：轮数上限或全员沉默**不等于任务成功，也不等于达成共识**。议程条件只决定「停止」，不宣称「达成」。

### 4.6 私有上下文（P3）+ 轮内并行（P4）

- **私有上下文**：每人一条 cursor + 增量投递，真正使用 `contextWindow` 分配 token 预算，永远保留「当前议题 + 最新增量」。
- **轮内并行**：同一快照并行推理 → 有序发布。保留可复现的 `rotation` 基线，逐步引入主持人策略。**不为每个事件调用所有 Agent 的 intent 模型**——确定性调度优先（轮转 / 点名 / 预算 / 跳过 / 等待 / 重复发言约束），仅在规则确实不够时再评估轻量模型选人。

## 5. 状态与可解释性模型

系统必须能分别回答三个问题，且答案必须是**可查的领域事实**，不是事后从日志里猜：

| 问题 | 答案来源（已落地） |
|---|---|
| ① 为什么**没获得发言机会**？ | `turn_end` 的客观清单（本轮谁发了言、是否被次数上限打断）＋ 各成员此刻的状态：`ACTIVE` = 没轮到 |
| ② 为什么**获得机会却没发言**？ | 它自己的 `silent` 事件（`SILENT` = 主动不说）＋ 被征询未表态会被记成 `PROPOSE_END`（现状：仍按结束处理，见下） |
| ③ 决定发言，**执行为什么没成功**？ | 这次发言是一条 `task`（`kind=session`、归属发言成员）：`task.status / error / trace` 可查；进程中断的残留被收成 `interrupted` |

### 5.1 轮次水位线与客观清单

- `turn_start`：人的一句新话开启新一轮，同时是**欲望有效期**的水位线（上一轮报的欲望到此作废）。
- `turn_end`：本轮结束的**客观清单**（`本轮结束：甲、乙 发言（发言次数已达上限）`）。

两者都不带状态跃迁、对 `states()` / `participants()` 透明。

### 5.2 【设计修正】不引入推断式 `reason_code`

原方案（沿 GPT6 的 `selection_status` / `participation_status` + `reason_code` 枚举）**被自己推翻**：

- `desire` 在本仓库里**只是排序依据，不是参与决策**——欲望低的人只要轮次预算没耗尽**依然会被叫到**。所以「因为欲望低所以没说」这个因果不成立，记为 `LOW_DESIRE` 就是**编出来的原因**。
- 被征询未表态者当前被直接记成 `propose_end`（`advance` 里「按结束处理」），同样是**把猜测写成事实**。
- 而 `DEFERRED` / `ROLE_NOT_RELEVANT` / `DEFERRED_BY_SCHEDULER` 这些候选值，在本仓库的决策路径上**根本不存在**。

**改为只记客观事实**：`turn_end` 的清单 + `selection` 级的「被选中」事件（`addressed` / `interject` / `floor_granted` 已有），
「为什么」交给**状态**回答（`SILENT` / `PROPOSE_END` / `ACTIVE` / `AWAIT_USER`）。
把猜测写成领域事实，比不记更糟——这条原则优先于枚举的整齐。
（若将来 `desire` 真的成为决策依据，再引入 `RANKED_LAST` / `TURN_BUDGET_EXHAUSTED` 也不迟，届时它才有真值。）

## 6. 发布与提交

**段级门控，不做 token 级**（因为 `speak` 工具整段返回，没有必要为理论上的细粒度取消引入当前架构不需要的复杂度）。若未来 `speak` 改为真正的 token 流式下发，再考虑 token 级，届时需额外定义「已展示的部分如何标记为中断、是否进入后续上下文」。

**两阶段逻辑模型**：

1. **生成**：Agent 在独立执行环境中生成完整发言。此时结果**尚未成为当前 Round 的正式发言**，不影响后续成员的讨论上下文。
2. **校验、发布与提交**：检查是否已取消、Round / Agenda 版本是否仍有效、发布权限是否满足；通过后发布整段发言，并提交为 Round 的正式结果。

**失败规则**：

| 情形 | 处置 |
|---|---|
| 生成期间被取消 | 丢弃未发布结果，不进入正式 Round 上下文 |
| 生成完成但版本校验失败 | 丢弃或归档为过期结果，不作为当前发言发布 |
| 校验通过 | 发布完整段落并提交正式发言记录 |
| 发布或提交部分失败 | 进入可恢复的失败处理路径 |

**用顺序消除窗口，而不是用补偿掩盖问题**：现状是「先发布后提交」（`SpeechSink#say` 立刻推流，整轮跑完才 `recordReply`），存在「用户已看到、库还没记」的真实窗口。改为**逐段落库（拿到 `message_id`）→ 再推前端**：

1. 一次 SQLite insert 的延迟可忽略；
2. `topic_event.message_id` 立刻能指回正本，`RoundtableTopicService` 那段「按 `event_seq` 水位线补写事件」的机制可以简化甚至删除；
3. 前端的「已中断」标记天然可信——**凡在库里的，都是已发布的**。

已发送到客户端的内容无法可靠撤回，因此前端必须明确区分「生成中」「已中断」「已完成」。

> **实施状态**：本节**尚未落地**（列为 P4 的前置条件之一，见 §7 的「P4 说明」）。
> 现状仍是「先发布后提交」：`SpeechSink#say` 一被调用就推流，整轮跑完才由 `recordReply` 落库;
> 于是「用户已看到、库还没记」的窗口在崩溃时才显形。做 P4（轮内并行）时必须先补上这一步。

## 7. 迁移路径与验收

| 阶段 | 内容 | 动范式 | 停下可交付 |
|---|---|---|---|
| **P0 正确性与安全边界** | ① 会话级串行写队列 + 停止改 runId（修 ③④）；② **只读由工具入口强制**（修 ⑦）；③ `desire` 两个缺陷（修 ⑧）；④ 梳理状态写入路径，消灭旁路 | 否 | 是 |
| **P1 非阻塞议程** | `advance` 拆成单次状态跃迁；协调器持状态与调度，模型/工具在外部异步跑；SSE 只订阅与投递；删 `SpeechPacer`（节奏归还前端） | 否 | 是 |
| **P2 持久化与恢复** | 划清领域事件 / 任务记录 / SSE 通知边界；为已接收未完成的执行建立可恢复状态；建立「发言提交 ↔ 通知投递」的可靠交接 | 否 | 是 |

> 本次核对代码后确认，它的前置条件是三件互相咬合的事：
> ① **发布与生成解耦**：`SpeechSink#say` 目前一被调用就推流，必须改成「整段生成 → 校验 → 发布」
> （即 §6 的段级门控，顺带把「先发布后提交」改成「先落库再发布」）；
> ② **状态动作改为缓冲后统一施加**：`propose_end` / `go_silent` / `interject` / `ask_user` 现在是
> 模型在发言中途调工具**就地生效**的；并行预生成时必须先攒着、到发布阶段按序施加，

> 这三件事无法在没有真实模型的情况下端到端验证，盲改会动摇系统最精细的一段。
> 按「每阶段停下都必须可交付」的原则，P4 留作独立一轮；P0–P3 已让它的地基到位
> （议程串行、发布侧唯一出口、事件 kind、任务留痕）。

- **P1**：模型调用期间用户输入与取消仍被及时处理；SSE 断开不使讨论生命周期与请求绑定。
- **P2**：进程退出后未完成任务不被误判为成功，也不无条件重复执行有副作用的操作。
- **P3**：轮次可见性与因果关系明确；上下文截断不会丢掉关键的最新输入。
- **P4**：同一轮发言互不污染；并行不导致不必要的 intent 调用与成本失控。
- **P5**：讨论、授权、执行可区分可追踪；重复执行与失败处理有明确策略。

> **每个阶段都要明确三件事**：必须保持的既有行为、需要修复的缺陷行为、新增行为，以及对应回归测试。
> 现有 `agent.roundtable` 只有 4 个测试（事件存储 / 随机策略 / 沉默复活 / 节流），**无一覆盖并发交错、停止竞争、版本校验、进程重启**——这是 P0 必须补的。

## 10. 结构变更的约定

库是由 `schema.sql` 里那些 `CREATE TABLE IF NOT EXISTS` 建的——**表已存在时建表语句是空操作，不会补新列**。
于是「给既有表加一列」这种变更，会让老库在新代码下当场报 `no such column`
（`chat_message.event_kind` 就这样炸过一次：代码是对的，库没跟上）。这属于**部署时**才会暴露的故障，
单测与编译都看不出来。

约定分两类：

| 变更类型 | 做法 |
|---|---|
| **加列**（可空、无默认值） | 在 `SchemaColumnPatches.PATCHES` 添一条，启动时幂等补齐。不动任何一行数据，老行取该列为 `NULL` |
| 其它（改列类型 / 重命名 / 删列 / 回填数据 / 建新表） | 直接改 `schema.sql`，并**重建库**（架构文档 STEP 7「DB 可破坏」） |

边界刻意划得窄：补丁一旦会改数据，「启动即执行」就不再是安全操作。加列之所以能自动化，
正因为它对已有数据是零风险的（幂等、可重复执行、失败即启动失败——不静默降级）。

> 排查同类问题的一条捷径：老库里 SEARCH 不到新列名，就说明缺列。本次即以此定位
> （库里能搜到 `event_seq`，搜不到 `event_kind`）。

### 10.1 验证编译必须用 `clean`

**IDE 会持续把 `.class` 写进 `target/classes`**，其时间戳比源文件新——于是 Maven 的增量检查
判定「无需编译」，`mvn test` 照样 `BUILD SUCCESS`，**哪怕源码里有编译错误**。

这个陷阱连着坑了两次：`List.of(new String[]{…})` 的 varargs 推断、以及 `List<Integer>.add(long)`。
两次都是「测试全绿」但真机一跑就炸，炸出来的还是 `java.lang.Error: Unresolved compilation problem`
（IDE 用错误恢复编出来的类，运行到那行才抛）。

**规则**：验证编译/测试一律加 `clean`（`mvnw clean test`）；只跑 `mvnw test` 得到的绿色不可信。
前端同理——`tsc -b` 也是增量的，要用 `tsc -b --force`。
