# 子代理与并行编码

## 评估

当前系统的三种对象承担不同职责：

| 对象 | 适合的工作 | 写代码方式 |
| --- | --- | --- |
| 普通子代理 `delegate_subagent` | 独立资料检索、方案比较、证据核查 | 协作项目中只读，不接管编码 |
| 编码专家 `delegate_agent` | Explore 定位、Planner 调研规划、Reviewer 审阅 | 共享当前任务副本，只读 |
| 编码任务 `coding_task` | 实施、构建、测试、形成可审阅差异 | 每个 TODO 独立副本，经另一成员检查后应用 |

原先的具体瓶颈：

- 自定义协作成员的子代理工具被协作过滤器移除；即使规程提到委派，模型也没有实际入口。
- 普通子代理只有后台回报语义，主控需要先取得调查结论再决策时不顺手。
- 协作计划只有一组 `todo/executor/reviewer`，并且每个成员只有一个 worker。编码模块已有并发能力，但主控无法派出一批工作。
- 编码主循环逐一等待同批专家调用，未设置后台模式时，独立专家也会串行执行。
- 原项目的全基准检查可以防覆盖，但直接并行后，后一份独立成果会因为前一份已应用而失效。不能简单放宽检查：不同文件也可能存在行为依赖，原先的测试未覆盖整合后的版本。

## 现在的工作流

主控继续负责计划与最终交付，只需要维护自己的业务提示词，不必创建多个永久编码 Agent。一个 Agent 配置可以产生多个独立执行实例。

1. 明确本次范围、验收标准和近期 TODO 的真实依赖。共享文件或接口需要共同修改时分批处理。
2. 调研用 `delegate_subagent`；当前决策依赖结果时传 `background=false`，直接取得结论；独立旁路调查可用默认后台模式。协作项目中显式点名写入/执行工具也不能越过只读边界。
3. 主控用 `start_work(assignments=[{id,reviewer},...],note=独立性与合入依据)` 明确派发 1–8 项已就绪工作；单项 `id/reviewer` 仍兼容。一项无效则整批不派发。
4. 每项工作独立绑定 TODO、执行身份、派工版本、代码副本和验证记录。同一成员的多项实施可同时运行，同一成员的独立检查依次处理。不会自动扩大计划或启动未派发的下游。
5. 编码运行与独立复跑共享 `MINIS_CODING_RUNS` 配置的并发名额，默认两个；额外工作进入有界队列。取消与派工失效也会终止排队工作。
6. 执行者在自己的副本完成实际验证后提交。检查者 `coding_task verify` 先同步项目中已接受的其他改动，再独立运行已记录的验证命令，并重新读取整合差异。
7. 只有验证绑定当前代码树且检查者明确接受后，系统才应用该版本。本批所有工作回报后主控统一决定下一批或交付。

## 版本与冲突保护

- 实施阶段不共写项目根目录。共享的是 Agent 配置，文件副本不共享。
- 同一待办的补充和续跑只能进入自己的副本；运行时绑定 TODO，模型不能通过参数选择另一个待办的执行授权。
- 整合只刷新本任务未修改的路径。双方修改同一路径时，包括同名新增、删除与修改、可执行位变化，立即拒绝，保留项目与副本。
- 不自动进行同文件文本合并。主控应依据两份 diff 决定一个明确的整合工作；不能重新发原实现或让后提交者覆盖前者。
- 整合使旧代码哈希和验证证据失效，随后重新构建/测试。不同文件之间的语义冲突由整合验证与独立审阅发现，文件不重叠本身不代表正确。
- 应用入口串行提交，并重新比较完整基准与产物版本。检查之后项目再次变化则拒绝应用，必须重新核对。
- 整合日志未完成时禁止继续或应用；失败尝试恢复副本，日志与两份成果保留以供诊断。
- 暂停、项目重新绑定、成员变更或派工版本变化会撤销相应执行授权。旧回报不能结算新派工。

WORKSPACE 沿用现有 Docker/SSH 环境，并非额外的操作系统沙箱。本次解决的是受控执行之间的副本与合入一致性；外部编辑器、其他服务或绕过工作目录的任意命令不属于文件系统事务。应用前检查会拒绝已观察到的变化，不承诺跨外部进程的分布式原子写入。

## 验证入口

后端重点：`RoundtableAutonomyTest`、`ParallelCodingAuthorityTest`、`CodingCompositionTest`、`CodingWorkspaceTest`、`CollaborationCodingLoopTest`、`WorkspaceProjectsTest`。覆盖相同配置并发、批次依赖校验、身份隔离、旧派工撤销、实际 Git 快照整合、同路径冲突和整合后的真实构建/测试。

前端：`npm --prefix frontend run build`、`test:collaboration`、`test:collaboration:browser`。计划面板展示本批在途数与逐项执行/检查信息。

这些测试验证运行机制，不证明真实模型必然主动委派或并行方案优于单 Agent。实际质量仍需使用相同真实业务工作比较完成质量、用户介入、时延与成本；本次没有使用真实模型及实际 SSH/Docker 项目做端到端验收。
