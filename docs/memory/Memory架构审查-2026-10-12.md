# 后端 Memory 架构审查

本文保留修复前的审查基准；后续已按本报告实施修复，详见 [Memory 架构修复说明](Memory架构修复说明-2026-10-12.md)。

审查日期：2026-10-12。设计基准：`四层Memory架构.md`。审查对象为当前工作区，包括尚未提交的实现；不以 memory-v2/v4/v5/v6 文档或代码注释自称实现了什么作为验收证据。本次没有修改后端实现。

## 结论

**架构骨架基本对齐，但关键隔离、写入治理、生命周期与检索保护尚未闭环，不能判定为符合设计大纲。**

已经有统一存储、四层/领域元数据、画像候选审批、工作集、发布与交接、执行快照、版本与撤销记录。这些方向正确。问题主要在端到端行为：某些读写入口绕过了层级语义，部分保护只在最后一步执行，部分能力仅有数据表和管理 API。

| 大纲要求 | 判断 | 实际情况 |
| --- | --- | --- |
| L1 长期共享，受控写入与版本管理 | 部分符合 | 画像有审批，项目共享事实仍可被普通 Agent 直接生成和改写 |
| L2 按 agentId 私有 | 部分符合 | AGENT 归属条目隔离；项目中的 L2 和自动提炼的方法经验没有保持同样边界 |
| L3 按 task/session 隔离，任务结束归档 | 部分符合 | 有工作集、检查点与 TTL，但项目 L3 可跨会话读取，蒸馏由普通轮末触发 |
| L4 显式发布、指定接收范围 | 部分符合 | 有发布授权和交接状态；PROJECT 读分支绕过发布范围，收件箱绕过有效性检查 |
| History / Working State / Long-term Memory 分离 | 存储符合，流程部分符合 | 三者有独立落点，自动提炼和轮末蒸馏仍把临时状态推向长期记忆 |
| 用户画像是受保护数据域 | 部分符合 | 普通自动提炼不直写画像，但自动候选缺证据引用，正常审批链无法完成 |
| 小说/角色扮演与真实身份隔离 | 部分符合 | 直接创作会话有 FICTION 闸门，子代理没有继承项目与身份 |
| 按需读取，避免记忆挤占 | 部分符合 | 有向量召回和分桶预算，但最新候选窗口、全库裁剪仍造成挤占 |
| 根据类型、证据、用户意图独立保留 | 不充分 | 未落地分域保留；遗忘墓碑没有覆盖普通长期记忆的自动重建 |
| 一轮快照、下一轮最新，权限紧急变更实时生效 | 部分符合 | 每轮构建快照，但没有找到运行中权限/指令强制刷新；回放引用不带版本 |

## 已确认的问题（按影响排序）

### 1. [P1] 原始事件召回绕过全部记忆作用域

位置：`KnowledgeToolbox.java:765`、`MemoryRecall.java:82`、`MemoryEventStore.java`、`MemoryWriter.java:77`。

普通 Agent 可以调用 `recall_memory(mode=event)`。该分支直接调用不带 MemoryExec 的事件召回，仅按时间、kind、actor 查询。事件写入也没有 projectId、agentId、sessionId 的归属字段。默认排除后台 actor 不构成权限隔离：其他项目/Agent 的用户和助手消息仍进入候选。

因此，即使 memory_item 的可见性正确，Agent 仍可通过原始事件读到其他项目/会话内容，违反大纲的默认隔离。

建议：事件保留来源作用域，事件下钻在 SQL 中执行同样的授权检查。历史无归属事件默认仅人工可查。

### 2. [P1] PROJECT 归属的读取忽略 L2/L3/L4 边界

位置：`MemoryPolicy.java:44`、`MemoryPolicy.java:95`、`MemoryExtractor.java:219`。

读谓词只要 `owner=PROJECT AND project_id=当前项目` 就放行，没有检查 layer。这使同项目的 L2 不受 agentId 限制，L3 不受 session/task 限制，L4 不需要命中共享授权。

例如，在项目 P 的会话 S1 中发布仅给 Agent B 的 L4 条目，同项目 Agent C 也可读到；撤销 share 后，PROJECT 分支仍然放行。与此同时，`ownershipFor()` 对项目中的 method/open_issue/episode 一律归 PROJECT，导致 Agent 的经验或未解决猜测也进入同项目共享面。

建议：Owner、Domain、Layer 分别表达归属、描述对象、可见性，不能让 PROJECT 分支吞掉所有层的约束。L2 按 Agent，L3 按任务/会话，L4 按发布授权；项目中的私有经验必须有可表达的组合。

### 3. [P1] 项目公共记忆缺少受控写入和质量闸门

位置：`MemoryExtractor.java:180`、`MemoryExtractor.java:208`、`MemoryEditService.java:123`。

模型输出 fact/decision/project 后，可直接写 PROJECT × L1 × active，证据引用为空，置信度没有写入门槛。`canEdit()` 对 PROJECT 只检查项目相等，允许当前项目的任意 Agent 改写项目 L1，甚至项目 L4。

乐观锁只能防并发覆盖，不能验证事实、区分作者权限或处理高风险决策。它不满足大纲“并非所有 Agent 都能随意修改公共 Memory”的要求。`canEdit()` 的 AGENT 分支也只排除 L4，没有对 L3 复核 session/task；按 item_id 定位时可编辑同 Agent 另一会话的 L3。

建议：把能读、能追加候选、能批准、能更新已确认共享知识分别定义；PROJECT L1/L4 更新须走授权和证据/冲突流程，已发布内容更新产生新版本并显式再发布。

### 4. [P1] 自动画像候选无法走完审批，来源证据没有闭环

位置：`MemoryExtractor.java:175`、`UserProfileService.java:75`、`UserProfileService.java:94`、`MemoryCandidateStore.java:44`。

自动提炼调用 `profiles.submit(..., evidenceRefs=null)`，即便用户明确说“记住”，submit 仍将证据等级降为 inferred。approve 又拒绝 inferred。因此正常自动候选不能通过现有批准接口转成正式画像。重复观察只增加 evidence_count，不会自动形成 repeated，也不追加证据引用。

候选没有携带 valid_until，approve 固定传 null，无法实现大纲 B 类“有时效性的用户状态”。submit 只拒 FICTION，没有按 PROJECT_PREF 做项目域分流；创作会话的 profile 草稿直接被丢弃，没有保留为项目内偏好。

建议：从消息/执行的真实来源 ID 开始贯通证据，区分用户原话、助手结论、推断与项目内偏好；按独立证据计数，审批保留有效期并检查真实身份来源。

### 5. [P1] 受保护记忆在预算保护之前就可能被淘汰

位置：`MemoryItemRecall.java:70`、`MemoryItemRecall.java:78`、`MemoryItemRecall.java:101`、`MemoryItemStore.java:276`、`MemorySnapshotBuilder.java:80`。

查询分支只对 pinned 豁免相关性门控，正式画像、directive、open_issue 并不豁免。没有 embedding 时 score=0，默认 min-score=0.35，非 pinned 的正式画像和全局指令会被直接丢弃。后续 fill 的 isProtected 预算豁免无法挽回。

候选先按最新 ID 截到 200 条；无查询分支又先截取较小 limit 再筛保护项。大量新增剧情条目可使更早的画像、指令和 pinned 条目根本进不了保护逻辑。分桶预算不能解决候选阶段的挤占。

建议：独立查询有效的保护集合，再合并各域相关候选，先按 scope 授权；保护集合不能依赖向量是否可用或最新候选窗口。

### 6. [P1] 情景保留上限是全库级，仍发生跨域记忆挤占

位置：`MemoryConsolidator.java:161`、`application.yaml:75`。

trimEpisodes 对全库 episode 取最新条目，默认仅保留 50 个，再把旧条目归档，没有按项目、Agent、任务或 retention=long 分开处理。

只要小说项目持续产出 50 条新 episode，其他 Agent 的旧 episode 就可能被归档，不再正常召回。这正是大纲“记忆挤占”和“独立保留”要解决的场景。

建议：按归属/领域制定独立配额和保留策略；长期保留、未解决、用户要求保留的记忆不应仅因其他域更活跃而归档。

### 7. [P1] 遗忘墓碑不能阻止普通记忆自动重建

位置：`MemoryEditService.java:113`、`MemoryPurgeService.java:76`、`MemoryExtractor.java:192`、`UserProfileService.java:71`、`MemoryItemStore.java:211`。

forget/purge 写了墓碑，但只有画像候选提交会检查 `revocations.blocked(fp)`。普通自动提炼仅通过 findByFingerprint 查 active/conflicted；被 revoked 的条目不算存在，相同内容再次出现在对话中就会插入新的 active 条目。

建议：所有自动新建入口共用墓碑检查，并按用户意图明确区分允许重新学习与禁止重建。遗忘还应撤销交接/共享发现路径。

### 8. [P1] 改写后正文、指纹和向量失去一致性

位置：`MemoryItemStore.java:368`、`MemoryItemStore.java:391`、`MemoryEditService.java:81`、`MemoryController.java:174`、`MemoryItemEmbeddingStore.java:58`。

改写只更新 title/body/source/version，没有重新计算 fingerprint，没有失效或重建 embedding。正文已经纠正，语义检索仍按旧内容向量打分；随后写墓碑也封锁旧指纹，去重依然依据旧内容。

恢复路径也存在缺口：itemsMissing 只 SELECT 旧版 14 个字段，却调用读取 user_id/owner/domain 等全部新列的 MemoryItemStore.map，实际补齐时会因缺列失败。没有找到条目 backfill 的生产调用方；工具 backfill_memory_vectors 只补事件向量。人工新增条目也未触发条目 embedding。

建议：更新操作在事务内更新正文和指纹、记录版本、使向量失效，提交后重算；修正缺向量查询的字段并接通可重试的条目补齐入口。

### 9. [P2] 工作集“收尾”绑定普通 Turn 完成，生命周期仍偏向 Turn

位置：`ChatTurnRunner.java:555`、`WorkingSetService.java:134`、`MemoryVocabulary.java:113`。

每个普通聊天 Turn 收尾都可能对更早的工作项调用 distill。这只是上一轮工作项，不代表任务已结束或结论已验证。distill 把内容异步送去提炼后立刻标 distilled，不能等待成功；模型未配置、提炼失败或返回空时也已关闭工作项。

自动 episode 默认落 L2（项目内也是 PROJECT L2），没有按任务生命周期归档的绑定语义。同时 fingerprint 和确定性/语义巩固同域键不含 session/task/layer；如果新增相同正文的 L3 条目，两个独立会话可能发生去重冲突或跨会话取代。

建议：用明确的任务完成/会话归档事件驱动蒸馏，暂停与普通 Turn 结束保留工作集；成功提炼后再确认蒸馏状态，并使 L3 幂等/巩固键含 session/task。

### 10. [P2] 子代理没有继承项目与角色身份

位置：`SubagentService.java:541`。

memScope 只带派发方 agentId 和 sessionId，projectId/taskId/turnId/identity 都为 null。派发自小说项目的子代理结论在提炼时变成无项目 AGENT 域，并以 INFERRED 身份运行，失去 FICTION 来源硬标记。

这会使创作材料进入 Agent 跨项目私有记忆，并可能形成画像候选（尽管问题 4 当前阻止其正常批准）。如果子代理被定义为临时执行体，继承派发方 agentId 本身合理；缺失项目与身份则是实际问题。

建议：派发时显式携带完整 MemoryExec，包含项目、任务和身份；仅按设计替换执行面及需要变化的 Agent 标识。

### 11. [P2] 交接只在管理侧闭环，且收件箱绕过撤销/过期

位置：`MemoryPublisher.java:114`、`MemoryPublisher.java:132`、`MemoryController.java:281`。

inbox 匹配目标后直接 findById 读正文，没有复核 memory_share 是否仍 published，也不检查条目 active、过期、superseded 或 revoked。撤销共享或遗忘后仍可在 offered 收件箱中看到内容。

只找到管理 API 调用 inbox/move，AgentRuntime 和工具没有接收/完成交接入口；普通语义召回能发现发布内容，但不等于完整交接状态机。to_kind=user 的交接也未在非人工 inbox 分支发现。

建议：收件箱复用有效性/发布权限检查，并给执行面提供按需列出与 accept/reject/done 的能力。大纲并未强制推送通知，采用拉取发现可以保留。

### 12. [P2] 快照审计与多表更新仍不满足版本化治理

位置：`MemorySnapshotStore.java:37`、`MemorySnapshotStore.java:45`、`MemoryItemStore.java:391`、`UserProfileService.java:88`、`MemoryPublisher.java:88`、`MemoryPublisher.java:161`。

快照只存 item IDs，水位是 max(id)，既不包含 item version，也不记录 work IDs。条目原地修改后，无法仅凭快照恢复当轮正文；revision 更新记录只含标题、版本和 source，不含完整 before/after body。max(id) 不随修改、撤销或权限变化增长。MemorySnapshot.fresh 没有找到生产使用点，也没有运行中指令/权限变更强制刷新。

画像批准（insert+candidate 状态）、handoff（share+offer）、提升（layer+promotion 状态）没有事务注解或事务调用边界；第二步失败会留下半完成状态。promoteLayer 还绕过组合矩阵，例如把 AGENT 条目提升为 L1，产生 insert 本来会拒绝的组合。

建议：快照记录条目版本和工作项引用，正文版本不可变或留完整修订记录；安全规则/权限使用递增版本并在必要的执行边界实时验证。多表动作使用事务，提升再次校验来源层、归属矩阵、证据和预期版本。

## 已经符合大纲的部分

- chat_message、memory_work、memory_item 分表，长期记忆没有直接复制全部历史消息。
- MemoryExec/MemoryScopeCtx 将执行身份与记忆访问连接起来；前台聊天入口传递项目与 FICTION 身份。
- 普通画像自动提炼进入候选，正式画像有独立 UserProfileService；直接 FICTION 画像候选被拒收。
- 默认条目召回通过 SQL 可见性过滤，再做语义打分，避免全量召回后才过滤私有条目。
- 使用统一存储，没有为每个 Agent 维护完整共享记忆副本。
- 有快照、分桶预算、轮内缓冲、版本 CAS、取代链、显式发布授权和工作集检查点恢复。
- 没有发现调度器直接持有或在每个 Turn 结束清空全部长期记忆。

MemoryService 不一定必须是一份同名巨型类；当前拆成多服务本身不违反大纲。真正需要收口的是各入口共同遵守的授权、质量、版本和生命周期规则。

## 验证范围与限制

实际执行并通过：

```powershell
.\mvnw.cmd -o '-Dtest=MemoryPolicyTest,MemoryPolicyConsistencyTest,MemoryScopeVisibilityTest,MemoryItemStoreTest,MemoryConsolidatorTest,MemoryTemporalTest,MemoryStageTest' '-DforkedProcessTimeoutInSeconds=60' test
```

共 29 个测试，0 失败、0 错误。另一次包括上下文注入/Mockito 测试的扩大运行停在 ContextInjectionProviderTest，已中止；不计入通过数量。没有执行真实 LLM/embedding 或线上数据库集成验证。

以上问题来自代码路径审查，不声称已经通过运行时复现全部问题。现有 SQL 与分支逻辑足以确认作用域、相关性门控、全库裁剪、证据缺失、更新一致性等行为；生产数据是否已经污染需要另行检查。

建议新增的验收场景：跨项目事件检索不能泄漏；同项目 L2/L3/L4 分别隔离；撤销发布后所有发现路径失效；无 embedding 时正式画像与指令仍可用；小说写满候选与情景配额不挤占其他域；明确画像陈述能带证据审批；forget 后相同材料不能重建；改写后向量/指纹一致；暂停多轮任务不提前蒸馏；创作子代理保持 FICTION。

## 修复顺序

1. 先修所有读入口的作用域与层级规则，尤其事件下钻、PROJECT 分支和交接收件箱。
2. 收口共享写入权限、保护集合检索、分域保留与遗忘闸门。
3. 贯通画像证据、更新指纹/向量和完整执行身份。
4. 最后完善任务生命周期、交接工具、事务与版本化回放。

当前不建议继续增加记忆表或新的概念层；优先把现有模块的行为边界修完整。
