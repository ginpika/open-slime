# 一、四层Memory架构

## L1 · Shared Memory（公共记忆）

用户长期偏好、全局规则、项目事实、已确认的决策。所有有权限的 Agent 都可以读取。

通常由统一的 Memory Service 管理，写入需要验证和版本控制。

## L2 · Agent Memory（私有记忆）

每个 Agent 的经验、偏好、判断习惯、失败记录、工作方法和未解决的问题。

按 agentId 隔离，默认不向其他 Agent 暴露。

## L3 · Task / Session Memory（任务记忆）

当前讨论内容、任务进度、临时结论、待办事项、工具执行结果、任务内共享的工作材料。

按 taskId / sessionId 隔离，任务结束后归档或清理。

## L4 · Handoff / Knowledge（交接与知识沉淀）

Agent 主动发布的结论、经过验证的经验、交接摘要、需要其他 Agent 关注的信息。

由发布机制控制可见范围，并非所有私有记忆都自动共享。

# 二、四层分别解决什么问题？

| 层级                | 作用域               | 生命周期       |
| ------------------- | -------------------- | -------------- |
| Shared              | 用户、工作区或项目   | 长期           |
| Agent               | Agent 身份           | 长期           |
| Task / Session      | 当前任务或会话       | 临时、可归档   |
| Handoff / Knowledge | 指定接收者或共享范围 | 由知识价值决定 |

# 三、独立 Memory 不等于独立对话历史

这是多 Agent 系统里很容易混淆的地方。

我建议明确区分以下三个概念：

- Conversation History： Agent 看过哪些消息、对话上下文是什么。
- Working State： Agent 当前正在做什么、任务执行到哪一步。
- Long-term Memory： Agent 从过去的任务中保留下来了什么。

举个例子：Developer 在任务中发现某个 Java API 存在并发问题。

这件事可以有三个不同的表示：

1. 对话历史：Developer 与 Planner 讨论了该 API 的行为。
2. 工作状态：当前任务正在将该 API 替换为线程安全的实现。
3. 长期记忆：在特定版本和使用条件下，该 API 存在已验证的并发风险。

三者不能混为一谈。

否则，你的系统很容易把一段对话中的临时假设直接沉淀为永久记忆，也容易在每次 Agent 恢复执行时重新加载过多历史消息。

# 四、最关键的问题：Agent 之间如何共享记忆？

我不建议采用「所有 Agent 都能随意写公共 Memory」的设计。

更稳妥的是引入一个明确的记忆写入与传播协议。

1. Agent 产生信息：事实、假设、结论、经验或任务进度
2. 判断信息类型与作用域：私有 / 当前任务 / 可共享 / 候选长期知识
3. 执行权限与质量检查：来源、置信度、冲突、时效性、访问权限
4. 发布到对应作用域：必要时通知订阅该信息的 Agent

例如，Developer 发现一个 Bug 后：

- 复现步骤和当前调试进度：写入 Task Memory。
- 该项目已经确认的技术约束：申请写入 Project Shared Memory。
- 自己尚未验证的怀疑：保留在 Agent Memory，或以明确标记的假设发布。
- 其他 Agent 需要继续处理的工作：通过 Handoff 发送交接材料。
- 已经反复验证、未来任务仍有价值的解决方案：沉淀为长期知识。

这样既保留了 Agent 的独立性，也避免了各自积累的信息成为孤岛。

# 五、落地上的一些思考

一个 Agent 可以在多个 Turn 中持续工作，也可以暂停一个任务后去处理另一个任务。因此，不能把 Memory 直接绑定到单个 Turn，更不能在 Turn 结束时就清空所有记忆。

可以采用下面的逻辑模型：

```
record MemoryScope(
    String ownerType,  // USER, PROJECT, AGENT, TASK
    String ownerId
) {}

record MemoryEntry(
    String id,
    MemoryScope scope,
    String type,       // FACT, PREFERENCE, DECISION,
                       // EXPERIENCE, HYPOTHESIS
    String content,
    String sourceId,
    String confidence,
    long version,
    Instant createdAt,
    Instant updatedAt
) {}
```

这只是概念模型。实际实现中，`confidence` 可以改为枚举或数值，时间字段可使用数据库时间类型；还应加入有效期、来源引用、权限、删除状态等字段。

## 建议的模块职责

| 模块                 | 职责                                             |
| -------------------- | ------------------------------------------------ |
| `MemoryService`      | 统一读取、写入、更新、检索和删除                 |
| `MemoryPolicy`       | 判断某个 Agent 能读什么、写什么                  |
| `MemoryRetriever`    | 按当前任务和 Agent 身份检索相关记忆              |
| `MemoryConsolidator` | 将有价值的任务经验整理为长期记忆                 |
| `MemoryPublisher`    | 将允许共享的信息发布到指定作用域                 |
| `AgentRuntime`       | 在执行时获取 Memory Snapshot，并管理当前工作状态 |
| `TurnScheduler`      | 负责调度与中断，不直接拥有长期记忆               |

特别注意：Memory Snapshot 应该是一次执行所使用的上下文视图，而不是把记忆永久复制进 Agent。

当任务运行期间公共记忆发生变化时，你可以根据一致性要求选择：

- 当前 Turn 使用启动时的快照。
- 下一个 Turn 读取最新版本。
- 对必须立即生效的安全规则或权限变更，使用强制刷新或实时校验。

这比让多个 Agent 在运行时随意修改彼此的上下文稳定得多。

# 六、我认为你最应该避免的三个设计陷阱

1. 每个 Agent 保存一份完整的共享记忆副本。

这种做法很快就会遇到同步、冲突和失效问题。优先使用统一存储与按需检索；确实需要缓存时，再设计版本和失效策略。

2. 所有 Agent 都可以自由修改公共记忆。

公共记忆一旦被错误信息污染，后续所有 Agent 都可能持续引用错误内容。至少应该区分普通追加、受控更新、冲突解决和高风险内容的确认流程。

3. 把所有历史消息都当作长期记忆。

多 Agent 群聊本身就会产生大量重复、争论、暂时性意见和无效输出。对话历史用于还原过程，长期记忆用于保存未来仍有价值的信息，两者应当分开治理。

# 七、解决现有问题

这三个问题不能单靠「每个 Agent 独立 Memory」解决，因为它们涉及的是记忆的归属、优先级、生命周期和写入权限。

## 记忆污染

小说里的人物、价值观、剧情决策，被错误地当成了用户本人的偏好和现实经历。

## 记忆挤占

连续几天都在写小说，大量剧情、设定和人物关系占据有限的记忆容量，让其他 Agent 的重要信息被挤出去。

## 记忆漂移

在小说项目中的临时决策，覆盖了其他 Agent 依赖的用户画像、项目事实或长期偏好。

# 八、领域概念——Memory Domain

我建议你不要只用 `USER / PROJECT / AGENT / TASK` 四种 Scope，而是引入一个更重要的概念：Memory Domain（记忆领域）。

因为即使两个记忆都属于同一个用户，它们也可能完全不应该互相影响。

1. User Profile · 用户画像

只记录跨场景、跨项目仍然成立的用户事实和稳定偏好。

例如：用户主要使用 Java 开发；偏好低成本、可长期维护的技术方案。

高保护等级 · 不允许普通 Agent 直接覆盖

2. Project Memory · 项目记忆

每个项目独立维护事实、决策、约束和当前进度。

例如：小说的世界观、人物关系、章节大纲；Personal Agent 的调度架构、技术决策。

项目间默认隔离 · 不能直接覆盖用户画像

3. Agent Memory · Agent 私有记忆

保存特定 Agent 的工作经验、判断、方法和未解决的问题。

例如：小说 Agent 对叙事节奏的总结；代码 Agent 对某类并发 Bug 的解决经验。

默认私有 · 经授权才可共享

4. Episodic / Task Memory · 事件与任务记忆

记录某次会话发生了什么、具体做了哪些决策，以及完整的工作材料。

例如：小说第三章的逐段修改、废弃剧情、人物对话、每次讨论的细节。

容量最大 · 按需检索 · 可归档

这里最重要的是：记忆归属不由「谁产生了这条记忆」决定，而由「这条信息描述的是什么、适用于什么范围」决定。

小说家 Agent 可以产生关于你的信息，但这不意味着这些信息应该进入用户画像。

# 九、用户画像应该改成「受保护的记忆」，而不是公共 Memory

我会将用户画像从普通共享记忆中独立出来，设计一个专门的 `UserProfileService`。

它不是普通 Agent 随时可以写入的知识库，而是一个需要证据和规则才能更新的受保护数据域。

建议将画像信息分为三类：

A. 稳定事实与长期偏好

例如使用的开发语言、长期工具偏好、明确要求的行为规则。

可以长期保留，修改需要充分证据。

B. 有时效性的用户状态

例如近期正在进行的工作、短期计划、当前关注的主题。

应该带有有效期，过期后降权或重新确认。

C. 待确认的画像候选

例如小说 Agent 发现你多次选择某种叙事风格，推测你可能偏好这种写法。

先记录证据，不直接升级为稳定画像。

更新流程应该类似这样：

```
Agent 观察到一条可能与用户有关的信息
              ↓
检查来源和适用范围
              ↓
是否只是当前项目中的选择？
       ├── 是 → 写入项目记忆
       └── 否 → 生成画像候选
                       ↓
              检查证据和历史记录
                       ↓
              符合自动更新规则？
                ├── 是 → 受控更新
                └── 否 → 等待更多证据或询问用户
```

举例来说，你连续三天都在小说项目中要求增加人物的心理描写。系统可以推断：

- 小说项目内，你当前偏好更细腻的心理描写。
- 你可能存在更广泛的叙事风格偏好。
- 但证据不足以证明你在阅读、游戏、电影乃至所有创作中都有相同偏好。

这就避免了单个 Agent 在一个项目中的高频交互，直接改变所有 Agent 对你的理解。

# 十、容易忽略的问题：同一用户可以有不同的上下文身份（role-play）

你可能会要求 AI 扮演某个角色，表达某种极端价值观，或者为了剧情作出与现实生活完全不同的选择。

系统必须明确区分：

- 用户在现实中的陈述。
- 用户对虚构角色的设定。
- 用户为了推进剧情作出的选择。
- 用户在某个项目中的创作偏好。
- 系统根据多次行为推断出的潜在偏好。

这不仅是记忆隔离问题，也是信息解释问题。

例如，小说角色讨厌某种事物，不代表用户讨厌它；角色经历某件事，也不代表用户本人经历过；你选择一种黑暗的剧情走向，也不代表这是你现实中的价值观。

因此，每条可能进入用户画像的记忆，都应保留来源类型。来自小说项目的内容默认只能形成项目内的画像或偏好，不能直接用于推断现实用户画像。

# 十一、设计理念（当你迷茫时可以以此为指导）

第一，隔离写入。 不同领域的记忆不能因为同一个用户、同一个 Agent 或同一个数据库，就默认拥有相同的写入权限。

第二，按需读取。 长期保存的知识可以很多，但每次模型调用只应该读取完成当前任务需要的信息。

第三，独立保留。 记忆是否重要、是否过期、是否应该保留，应该由类型、证据、明确的保留策略和用户意图决定，而不是由最近是否活跃决定。
