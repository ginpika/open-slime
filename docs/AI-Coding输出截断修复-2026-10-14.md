# 编码任务单次输出截断修复

2026-10-15 更新：累计 token 额度现已默认关闭（`MINIS_CODING_MAX_TOKENS=0`）；活动状态、推理展示与工具位置的修复见 [最新记录](AI-Coding活动状态与任务过程修复-2026-10-15.md)。下文记录 10 月 14 日的单次输出修复。

2026-10-14。用户报告普通编码任务在 8192 tokens 后提示“模型输出达到上限；未执行截断的工具调用，检查点已保存”。这是此前实现的缺陷：CodingFacade 强制发送 `max_tokens=min(8192, contextWindow/4)`，并将 `finish_reason=length` 直接视为必须暂停的上下文溢出。

8192 是这次响应的输出上限，不是整个编程任务可以使用的总 token 数。把上下文窗口除以四也不能推断模型支持的输出能力。

## 修复后的行为

- 默认不发送人为设定的 `max_tokens`，由模型服务决定单次输出；不猜测某个服务的输出能力。
- 模型设置新增“单次输出上限”，独立保存为 `llm_model.max_output_tokens`。仅用于编码任务，留空保持服务默认；需填写服务实际支持的值，不会扩大服务自身的硬限制。
- 指定上限时优先使用该模型配置，再使用 Coding 模块的可选全局上限；请求仍为输入上下文留出空间，不把整个窗口都分给输出。
- 模型响应结束原因为 length 时，先统计预算、记录截断事件，再保存文本和续接指令。该响应所有工具调用均不派发，半截 JSON、缺失 ID 和完整但处于同一截断响应中的调用都不执行。
- 自动继续下一轮，明确告知模型本轮工具未执行，要求小步读取、小片段补丁和分段创建长文件，避免重复长篇分析或一次输出整个项目。
- 纯思考截断也可以续接，不当作空回答失败；同一次执行内的长文本回答片段在最终回答中拼接保留，不把思考内容冒充正文。
- 默认最多连续自动续接 3 次；第 4 次连续截断仍保存检查点后暂停。完整响应会重置连续计数，所有请求仍受轮数、时间、取消和累计 token 预算约束。
- 工作台显示“单次输出达到模型上限，已自动续接”，不会在第一次截断时直接变成暂停。连续失败时提供模型设置入口。

底层 ModelLoop 增加默认关闭的 `continueAfterResponse` 钩子，在接纳/执行工具前供 Coding 决定续接；普通聊天和其他调用方继续使用原有策略。OpenAiChatClient 直接保留结束原因，旧两参数 RawResult 构造仍兼容原响应封装。

CodingContext 的压缩预留与实际请求输出配置对齐。默认预留 32768 只是上下文规划用的容量，不会变成请求中的固定输出上限，也不会产生新的“跑到 32768 就停止”的单次暂停条件。

## 配置与使用

| 配置 | 含义 |
| --- | --- |
| 设置 → 大模型 → 编辑 → 单次输出上限 | 可选的模型级编码输出上限；留空跟随服务，修改上下文窗口不会修改此项 |
| `MINIS_CODING_RESPONSE_TOKENS=0` | 可选模块全局输出上限，0 为不指定；模型级设置优先 |
| `MINIS_CODING_RESPONSE_RESERVE=32768` | 未指定输出能力时的上下文预留，按窗口安全收敛 |
| `MINIS_CODING_OUTPUT_CONTINUATIONS=3` | 最大连续自动续接次数 |
| `MINIS_CODING_MAX_TOKENS=200000` | 当前执行累计请求/响应的估算预算，与单次输出不同 |

新字段通过现有 SchemaColumnPatches 幂等补列。旧模型、端点、API key 和上下文窗口保留，新字段初始为空。没有修改用户实际运行数据库，也没有提升 SSO/工作空间权限。

部署新后端并重启后，原先暂停的任务可以使用“继续”恢复，不必删除项目或重新登记仓库；已有检查点和原任务授权保留。设置页与续接提示需要新前端构建。模型服务的硬输出限制仍然有效；如果服务默认输出仍不足，可配置其支持的单次输出上限。

- 后端选定 69 项回归全部通过。新增 8 项输出策略测试、3 项模型设置/旧库迁移测试，并覆盖既有普通聊天、圆桌、编码状态/权限/架构分层。

- 覆盖纯思考截断、文本回答拼接、连续失败上限、完整响应重置计数、旧响应封装结束原因和恢复请求计入原轮数预算。
