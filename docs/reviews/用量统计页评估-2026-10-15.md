## 原始评估（改进前快照）

## 结论与现有优点

当前页面适合粗看应用累计 Token 消耗，不足以可靠评估金额，也不能直接作为账单依据。最优先的问题是时间范围与汇总数据不一致；在修正统计可信度之前，不宜简单将总 Token 乘以一个单价来显示费用。

已有基础值得保留：输入与输出分开统计、来源和模型分布、按日趋势补零、读取失败后的重试及旧数据提示，以及通过 `alive` 标记避免快速切换区间时旧请求覆盖新请求。

## 已确认的错误

### 1. P1：顶部时间范围与实际统计范围不一致

- 前端 `frontend/src/pages/Stats.tsx:161` 将总 Token 标为“最近 N 天”。范围按钮位于整页标题处，容易让人理解为整页筛选。
- `backend/src/main/java/cc/ginpika/minis/stats/TokenUsageService.java:99` 中，`days` 只作用于 `daily(since)`；`totals()`、`bySource()`、`byModel()` 均查询全部历史，没有时间条件。
- 已直接提取 `TokenUsageStore` 的实际查询，在内存 SQLite 中插入 40 天前的 1,000 Token 与今天的 100 Token：7 天和 30 天的趋势均为 100，总量及两种分布均为 1,100；90 天才一致。
- 影响：用户会高估近期用量；筛选前后总量不变，且无法与趋势对账。
- 建议：总量、来源、模型、趋势统一使用同一个 `[from, to)` 查询窗口；如保留累计总量，应独立标注“全部历史”。

### 2. P2：部分 usage 被当作完整的实测数据

- `backend/src/main/java/cc/ginpika/minis/ai/llm/OpenAiChatClient.java:400` 只要存在输入或输出任一字段就采信 usage；缺失字段以 0 计，并标为真实用量。
- `EmbeddingClient.java:104`、`RerankClient.java:103` 允许只返回 `total_tokens`，此时输入为 0，总量仍可大于 0。
- 前端趋势仅显示输入、输出，占比又以二者之和为分母，因而可能出现总量有消耗、趋势没有对应输入，或输入输出占比无法说明总量的情况。
- 建议：区分完整实测、部分实测、估算与未知；无法拆分的量单独展示，不将缺失字段解释为实际为零。对单纯输入型接口，可在协议明确时从总量回填输入。

## 从代码确认的风险

### 3. P1：中断、取消或解析失败的请求可能漏记已产生的消耗

- `backend/src/main/java/cc/ginpika/minis/ai/llm/OpenAiChatClient.java:224` 只有 `readStream` 成功返回后才执行 `recordUsage`。
- `readStream` 在流未完成时直接抛错（第 350 行）；即使供应商已经生成部分输出，也不会经过正常记账路径。
- 影响：失败和重试较多时，页面可能低估实际消耗；供应商是否收费需以其账单为准，不能假设所有失败请求都收费或都免费。
- 建议：保留每次实际请求及其状态；中断时尽量记录已收到的 usage 或部分估算，并将未知部分明确标示。重试应记录为独立请求。

### 4. P2：服务器与浏览器时区不同，会导致日期错位或补零遗漏

- 后端窗口使用 JVM 默认时区，按日分组使用 SQLite `localtime`；前端 `fillDays`（`Stats.tsx:42`）使用浏览器本地日期生成横轴。
- 接口不返回统计时区、明确起止日期或服务器日期。同一时刻若服务器为 UTC、浏览器为 UTC+8，凌晨时双方“今天”可能不同。
- 建议：由接口返回唯一时区及完整日期序列，所有聚合共用该口径；前端展示时区与精确日期范围。

## 对成本评估目标的功能缺口

### 5. P1：没有金额模型，不能回答“花了多少钱”

- `token_usage` 仅保存来源、模型名、输入、输出、总量、估算标记及时间（`backend/src/main/resources/schema.sql:882`）。
- 缺少供应商/端点标识、计费模型标识、币种、单价及其生效时间，也没有实付金额或供应商账单接入。
- 同名模型经不同供应商调用会在 `byModel()` 中合并，无法区分不同价格；缓存命中、缓存写入及推理 Token 等细分用量未保留，也难以按不同计费规则准确估价。精排等服务还可能使用非 Token 计价。
- 建议：先支持用户配置按供应商和模型区分的价格与币种，保存调用时的价格快照；缺少价格时显示“未定价”，并列出未计价用量。明确区分“估算费用”和“实付账单”，不要把未知费用显示为 0。

### 6. P2：实测与估算混合展示，可信程度不可见

- 数据库有 `estimated` 字段，但 `StatsDtos` 的聚合响应未包含估算调用数或估算 Token 数，页面没有任何提示。
- 本地估算采用中文字符约 1 Token、其他字符约 4 字符 1 Token 的简化规则，不能代表各模型真实 tokenizer 或多模态计费。
- 建议：展示实测/估算/未知的调用数及用量构成；费用估算沿用数据质量标记。落库失败当前只写日志，也应提供记录完整性提示或监控。

### 7. P2：能看分布，但难以定位贵在哪里、为什么变贵

- 来源与模型只显示总 Token 和调用数，不能查看输入/输出明细、成本占比、每次平均成本或调用记录。
- 没有按供应商、会话、Agent、圆桌或编程任务追溯的维度；很多智能体调用最终都记为 `chat`。
- 模型测试来源也不完全统一：聊天测试使用 `model-test`，Embedding/Rerank 测试经过客户端后仍归入向量化/精排。
- 建议：支持“来源 → 模型 → 调用/任务明细”的逐层查看，展示输入、输出、缓存、状态及估算费用；用途与调用类型分别记录，避免一个 source 同时承担两个含义。

### 8. P2：缺少持续评估与控制工具

- `Stats.tsx:101` 仅在挂载、切换天数或错误重试时读取；成功状态没有刷新按钮、更新时间或自动更新，页面停留期间新增消耗不可见。
- 只有最近 7/30/90 天，没有自然月、自定义日期、上期对比、预算、超额提醒或导出。
- 建议：先补手动刷新、更新时间、当月/自定义区间及 CSV 导出；随后加入环比、日均费用、明确注明依据的月末预测和预算提醒。

## 展示与可访问性不足

- Flat/Endfield/BlueArchive 的若干常规标签、提示复用了 `text-2xs` / `ui-label`，实际映射为 11px；Flat 分布值与范围按钮为 `text-sm`，实际为 13px。按 `docs/ui-design-font-size.md`，常规正文应至少 14px、次要信息通常至少 12px、按钮优先 14–16px。Flat 页面标题为 22px、部分区块标题为 13–16px，也低于文档建议的标题层级。需要按页面用途调整，避免直接改全局字号影响其他页面。
- `StatsTrendChart.tsx:121` 仅输出 Canvas 容器，没有可读取的每日数据表或文字替代；键盘与读屏用户难以取得趋势明细。部分主题的范围按钮也没有程序化的选中状态。
- 来源/模型条形长度是相对于最大项，未明确说明，并不表示占总用量的百分比；建议同时显示真实占比和单位。
- Astrolabe 分布中的模型名可能被截断，缺少完整名称查看入口；模型较多时列表没有排序、搜索或收起功能。
- 趋势采用平滑曲线，但数据是每日离散总量，可能造成日内变化的暗示；建议采用柱图或直线，并支持查看每日明细。

本次未进行浏览器视觉验收，未验证移动端、200% 缩放或各主题的实际对比度；这些仍需实际渲染检查。

## 建议实施顺序

1. 先修可信度：统一时间窗口/时区，修正部分 usage 处理，展示估算与未知，补中断请求记录和统计回归测试。
2. 再补成本：供应商与模型计价配置、价格快照、币种、估算金额及未定价覆盖率；已有历史记录无法还原价格时明确标注。
3. 最后增强决策：任务追溯、自然月/自定义区间、刷新与导出、对比和预算，并补齐字体与可访问性验收。

## 验证范围

- 导航及面包屑现有测试：5 项通过。
- 前端 `npm run build` 通过；构建仍提示主 JS 包超过 500 kB，这是现有打包体积提醒。
- 范围错误：使用实际 Store SQL 的内存 SQLite 复现，不读取或修改用户数据库。
- 其他结论：基于当前工作区的页面、PageKit、API、统计 SQL、数据库结构及模型客户端调用路径检查；未使用供应商真实账单做核对。
